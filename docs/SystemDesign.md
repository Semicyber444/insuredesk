# System Design: ระบบค้นหาและเปรียบเทียบประกันรถยนต์ภายในทีม

## 1. ภาพรวมโครงการ

ระบบเว็บสำหรับสมาชิกภายในทีม 3 คน ใช้จัดเก็บ ค้นหา และเปรียบเทียบข้อมูลประกันรถยนต์จากหลายบริษัท โดยแสดงราคา ทุนประกัน เงื่อนไขรถ ความคุ้มครอง และเอกสารอ้างอิงอย่างเป็นระบบ

โครงการเริ่มต้นโดยยังไม่มีข้อมูลประกัน จึงต้องรองรับการกรอกข้อมูลด้วยตนเองและตรวจสอบข้อมูลก่อนเผยแพร่ให้ทีมค้นหา

ผู้พัฒนายังไม่มีประสบการณ์ JavaScript/React ระบบจึงเน้นโครงสร้างเรียบง่าย ใช้บริการสำเร็จรูปในส่วนฐานข้อมูล การเข้าสู่ระบบ และการเก็บเอกสาร

### 1.1 เป้าหมาย

- รวบรวมข้อมูลประกันไว้ในแหล่งเดียว
- ลดเวลาการเปิดเอกสารเพื่อค้นหาเงื่อนไข
- เปรียบเทียบแพ็กเกจโดยเห็นข้อแตกต่างและข้อจำกัด
- ตรวจสอบกลับไปยังเอกสารต้นทางได้
- เก็บประวัติราคาและเงื่อนไขโดยไม่แก้ทับข้อมูลที่เผยแพร่แล้ว
- จำกัดการเข้าถึงเฉพาะสมาชิกที่ได้รับอนุญาต

### 1.2 ผู้ใช้งานและสภาพแวดล้อม

| รายการ | รายละเอียด |
|---|---|
| จำนวนผู้ใช้งานเริ่มต้น | 3 คน |
| กลุ่มผู้ใช้งาน | ทีมภายใน |
| อุปกรณ์หลัก | คอมพิวเตอร์ Windows และ Mac |
| วิธีใช้งาน | เว็บเบราว์เซอร์ |
| ภาษา | ภาษาไทย |
| สกุลเงิน | บาท |
| ลักษณะระบบ | ฐานข้อมูลเพื่อค้นหาและเปรียบเทียบ ไม่ใช่ระบบเสนอราคาหรือรับประกันอัตโนมัติ |

## 2. ขอบเขต

### 2.1 รวมในเวอร์ชันแรก

- เข้าสู่ระบบด้วยบัญชีที่ได้รับเชิญ
- จัดการข้อมูลบริษัทประกัน
- จัดการแพ็กเกจและรุ่นของเงื่อนไข
- บันทึกคุณสมบัติรถที่รับประกัน
- บันทึกตัวเลือกราคาและทุนประกัน
- บันทึกความคุ้มครอง บริการเสริม และข้อยกเว้น
- แนบเอกสารอ้างอิง
- ตรวจสอบและเผยแพร่ข้อมูล
- ค้นหาและกรองแพ็กเกจ
- เปรียบเทียบตัวเลือกประกัน 2–4 รายการ
- บันทึกประวัติการเปลี่ยนแปลง

### 2.2 ยังไม่รวมในเวอร์ชันแรก

- ซื้อประกันหรือรับชำระเงิน
- ออกกรมธรรม์
- จัดเก็บข้อมูลลูกค้า
- ขอใบเสนอราคา
- เชื่อม API บริษัทประกัน
- ดึงข้อมูลจากเว็บไซต์อัตโนมัติ
- คำนวณเบี้ยโดยไม่มีตารางอัตราที่ได้รับมา
- AI อ่านเอกสารหรือแนะนำประกัน
- นำเข้า Excel แบบอัตโนมัติ

การนำเข้า Excel เป็นงานระยะถัดไป หลังจากโครงสร้างข้อมูลผ่านการทดลองใช้งานแล้ว

## 3. หลักการออกแบบ

- ความถูกต้องและการตรวจสอบย้อนหลังสำคัญกว่าจำนวนข้อมูล
- ข้อมูลไม่ทราบต้องไม่ถูกแสดงเป็น “ไม่คุ้มครอง” หรือ “0 บาท”
- ราคาแต่ละรายการต้องผูกกับเงื่อนไขรถและทุนประกันที่ใช้ได้จริง
- ข้อมูลที่ตรงกับตัวกรองไม่เท่ากับการยืนยันรับประกัน
- เอกสารและฐานข้อมูลต้องไม่เปิดสาธารณะ
- ข้อมูลที่เผยแพร่แล้วต้องแก้ผ่านรุ่นใหม่
- ไม่ใช้ระบบค้นหาแยกต่างหากหรือ microservices ในระยะแรก
- ข้อมูลสมมติต้องแยกจากข้อมูลใช้งานจริงและติดป้ายชัดเจน

## 4. เทคโนโลยี

| ส่วน | เทคโนโลยี | หน้าที่ |
|---|---|---|
| Web application | Next.js + TypeScript | หน้าเว็บและการทำงานฝั่งเซิร์ฟเวอร์ |
| UI styling | Tailwind CSS | รูปแบบหน้าจอ |
| Database | PostgreSQL ผ่าน Supabase | จัดเก็บข้อมูลเชิงสัมพันธ์ |
| Authentication | Supabase Auth | เข้าสู่ระบบและจัดการ session |
| File storage | Supabase Storage | เก็บเอกสารใน private bucket |
| Validation | Zod | ตรวจสอบข้อมูลที่รับจากแบบฟอร์ม |
| Source control | Git + private GitHub repository | เก็บโค้ดและประวัติการเปลี่ยนแปลง |
| Hosting | บริการที่รองรับ Next.js เช่น Vercel | ให้ทีมเข้าใช้งานเว็บออนไลน์ |

เลือกเวอร์ชันเสถียรที่รองรับกัน ณ วันที่เริ่มติดตั้ง และบันทึกเวอร์ชันผ่าน package.json กับ lockfile

ค่าใช้จ่ายและข้อจำกัดของบริการต้องตรวจสอบก่อนเปิดใช้งานจริง ไม่สมมติว่าแผนฟรีครอบคลุมการใช้งานทั้งหมด

## 5. สถาปัตยกรรม

Browser
→ Next.js application
→ Supabase Auth / PostgreSQL / Private Storage

### 5.1 Browser

- แสดงแบบฟอร์ม ผลค้นหา และตารางเปรียบเทียบ
- ส่งคำขอพร้อม session ของผู้ใช้
- ไม่เก็บกุญแจลับที่มีสิทธิ์ผู้ดูแล
- ไม่เป็นผู้ตัดสินสิทธิ์การเข้าถึงขั้นสุดท้าย

### 5.2 Next.js

- ตรวจสอบ session
- ตรวจสอบสิทธิ์ก่อนอ่านหรือเปลี่ยนข้อมูล
- ตรวจสอบรูปแบบข้อมูลฝั่งเซิร์ฟเวอร์
- เรียกฐานข้อมูลภายใต้สิทธิ์ของผู้ใช้
- จัดการการอัปโหลดเอกสารและเปิดเอกสารอย่างมีสิทธิ์
- ไม่เก็บผลตอบกลับที่มีข้อมูลส่วนตัวใน shared public cache

### 5.3 Supabase

- Auth จัดการบัญชีและ session
- PostgreSQL จัดเก็บข้อมูลและบังคับใช้ข้อกำหนด
- Row Level Security หรือ RLS จำกัดการเข้าถึงรายตาราง
- Private Storage เก็บเอกสารและตรวจสิทธิ์การดาวน์โหลด

การซ่อนปุ่มหรือการ redirect หน้าเว็บไม่เพียงพอ ต้องมีการตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์และฐานข้อมูลด้วย

## 6. บทบาทและสิทธิ์

บัญชีหนึ่งมีได้มากกว่าหนึ่งบทบาท

| บทบาท | ความสามารถ |
|---|---|
| viewer | ค้นหา เปรียบเทียบ และอ่านข้อมูลที่เผยแพร่แล้ว |
| editor | สิทธิ์ viewer และสร้างหรือแก้ไขข้อมูลร่าง อัปโหลดเอกสาร ส่งตรวจ |
| reviewer | สิทธิ์ viewer และตรวจสอบ ส่งกลับแก้ไข หรือเผยแพร่ข้อมูล |
| admin | จัดการสมาชิก บทบาท และจัดเก็บรายการที่เลิกใช้งาน |

สำหรับทีม 3 คน แนะนำให้แบ่งผู้กรอกและผู้ตรวจสอบข้อมูลออกจากกันเมื่อทำได้

หาก admin จำเป็นต้องเผยแพร่ข้อมูลที่ตนเองแก้ไข ต้องบันทึกเหตุผลการยกเว้นไว้ในประวัติ

การสร้างบัญชีและเปลี่ยนบทบาททำผ่านขั้นตอนสำหรับผู้ดูแลเท่านั้น ผู้ใช้ห้ามแก้บทบาทของตนเองผ่าน API ทั่วไป

## 8. แบบจำลองข้อมูล

### 8.1 ข้อกำหนดร่วม

- ใช้ UUID เป็น primary key
- ใช้ foreign key เชื่อมข้อมูลที่เกี่ยวข้อง
- ใช้ numeric สำหรับจำนวนเงิน ไม่ใช้ floating point
- เก็บวันเริ่มต้นและวันสิ้นสุดเงื่อนไขเป็น date
- เก็บเวลาการทำงานเป็น timestamptz และแสดงผลตาม Asia/Bangkok
- เก็บปีรถเป็น ค.ศ. และระบุรูปแบบให้ชัดเจนในหน้าจอ
- ใช้ NULL แทนค่าที่ยังไม่ทราบ
- เก็บ created_at, updated_at, created_by และ updated_by ในตารางที่แก้ไขได้
- ห้ามลบข้อมูลที่ถูกใช้ในรุ่นเผยแพร่แล้ว ให้ archive แทน
- ข้อมูลบริษัทและรุ่นรถที่เลิกใช้งานต้องยังอ่านย้อนหลังได้

### 8.2 ตารางหลัก

| ตาราง | หน้าที่ | ฟิลด์สำคัญ |
|---|---|---|
| profiles | ข้อมูลสมาชิก | user_id, display_name, is_active |
| user_roles | บทบาทสมาชิก | user_id, role |
| insurers | บริษัทประกัน | id, name, contact_channels, website, is_active |
| plans | ตัวตนของแพ็กเกจ | id, insurer_id, name, insurance_type, is_archived |
| plan_versions | รุ่นเงื่อนไข | id, plan_id, version_no, workflow_status, effective_from, effective_to, verified_at, review_due_at |
| vehicle_models | รุ่นรถ | id, brand, model, variant, powertrain |
| eligibility_rules | เงื่อนไขรถ | id, plan_version_id, scope_type, vehicle_model_id, min_age, max_age, age_basis, usage_type, notes |
| price_options | ตัวเลือกราคา | id, eligibility_rule_id, label, repair_type, price_type, premium_total, sum_insured_min, sum_insured_max, deductible_amount, deductible_terms, valid_from, valid_to |
| coverage_types | หมวดความคุ้มครอง | id, code, name, category, sort_order |
| version_coverages | ความคุ้มครองพื้นฐานของรุ่นแผน | id, plan_version_id, coverage_type_id, status, limit_amount, limit_basis, deductible_amount, terms, exclusions |
| option_coverage_overrides | ความคุ้มครองที่ต่างในแต่ละตัวเลือก | id, price_option_id, coverage_type_id, status, limit_amount, limit_basis, deductible_amount, terms, exclusions |
| source_documents | เอกสารและแหล่งอ้างอิง | id, plan_version_id, source_type, storage_path, source_url, title, received_at |
| audit_logs | ประวัติการเปลี่ยนแปลง | id, actor_id, action, entity_type, entity_id, before_data, after_data, reason, created_at |

### 8.3 ความสัมพันธ์

- บริษัทหนึ่งมีหลายแพ็กเกจ
- แพ็กเกจหนึ่งมีหลายรุ่นเงื่อนไข
- รุ่นเงื่อนไขหนึ่งมีหลายกฎรับประกันรถ
- กฎรับประกันรถหนึ่งมีหลายตัวเลือกราคา
- รุ่นเงื่อนไขหนึ่งมีหลายความคุ้มครองและเอกสาร
- ตัวเลือกราคาสามารถกำหนดความคุ้มครองทับค่าพื้นฐานได้

หากไม่มี override ให้ใช้ความคุ้มครองพื้นฐานของรุ่นแผน

หากมี override ให้ใช้ข้อมูล override ทั้งรายการ ไม่รวมค่าบางช่องจากพื้นฐานโดยอัตโนมัติ เพื่อหลีกเลี่ยงการนำเงื่อนไขคนละชุดมาปะปน

### 8.4 ข้อกำหนดความถูกต้อง

- คู่ plan_id และ version_no ต้องไม่ซ้ำ
- ความคุ้มครองชนิดเดียวกันต้องไม่ซ้ำในรุ่นแผนเดียวกัน
- override ชนิดเดียวกันต้องไม่ซ้ำในตัวเลือกเดียวกัน
- ราคา ทุน และอายุรถต้องไม่ติดลบ
- ค่าขั้นต่ำต้องไม่เกินค่าสูงสุด
- วันสิ้นสุดต้องไม่ก่อนวันเริ่มต้น
- ตัวเลือกราคาต้องเชื่อมกับกฎรับประกันที่ระบุขอบเขตชัดเจน
- การเผยแพร่ต้องมีแหล่งอ้างอิงและผู้ตรวจสอบ
- การเปลี่ยนข้อมูลพร้อมกันต้องตรวจ updated_at หรือ revision เพื่อไม่ให้บันทึกทับงานกันโดยไม่แจ้งเตือน

## 9. รายละเอียดข้อมูลประกัน

### 9.1 ประเภทประกัน

รองรับประเภท:
- ชั้น 1
- ชั้น 2+
- ชั้น 3+
- ชั้น 2
- ชั้น 3

ประเภทประกันไม่ใช่หลักฐานว่ารายการใดคุ้มครอง ต้องอ้างอิงรายละเอียดของแผนนั้นเสมอ

### 9.2 เงื่อนไขรถ

บันทึกข้อมูล:
- ยี่ห้อ รุ่น และรุ่นย่อย
- อายุรถขั้นต่ำและสูงสุด
- หลักเกณฑ์การนับอายุรถ
- ลักษณะการใช้งาน
- ระบบขับเคลื่อน หากเกี่ยวข้อง
- เงื่อนไขการตรวจสภาพ
- ข้อจำกัดเพิ่มเติม

scope_type ต้องแยกอย่างน้อย:
- specific_model: ระบุรุ่นรถ
- all_models: เอกสารยืนยันว่ารองรับทุกรุ่นภายใต้เงื่อนไข
- unknown: ยังไม่ทราบขอบเขต

ห้ามตีความ vehicle_model_id ที่เป็น NULL ว่าใช้ได้กับรถทุกรุ่น

### 9.3 ราคา

price_type รองรับ:
- starting: ราคาเริ่มต้น
- indicative: ราคาประมาณการ
- fixed_for_conditions: ราคาที่ระบุสำหรับเงื่อนไขนี้
- unknown: ยังไม่มีราคา

ข้อมูลประกอบราคา:
- เบี้ยสุทธิ ภาษี และอากร หากมี
- ยอดชำระรวม
- การรวม พ.ร.บ.: รวม / ไม่รวม / ยังไม่ระบุ
- ทุนประกัน
- การซ่อม
- ค่าเสียหายส่วนแรกและเงื่อนไข
- ข้อสมมติหรือเงื่อนไขผู้ขับขี่ หากมี
- วันเริ่มต้นและวันสิ้นสุดราคา

หากไม่มีราคา ให้แสดง “ยังไม่มีข้อมูลราคา” และไม่แทนด้วย 0 บาท

หากเอกสารให้เฉพาะราคาเริ่มต้นหรือช่วงทุน ต้องแสดงตามนั้น ไม่คำนวณราคาสำหรับทุนอื่นขึ้นเอง

### 9.4 ความคุ้มครอง

สถานะมาตรฐาน:
- covered: คุ้มครอง
- not_covered: ไม่คุ้มครอง
- optional: ซื้อเพิ่มได้
- unknown: ยังไม่ระบุ

หมวดเริ่มต้น:
- ความเสียหายต่อรถผู้เอาประกัน
- ความรับผิดต่อบุคคลภายนอก
- รถพลิกคว่ำ
- น้ำท่วม
- รถยนต์สูญหายหรือถูกโจรกรรม
- ทรัพย์สินภายในรถถูกโจรกรรม
- กระจกบังลมเสียหาย
- อุบัติเหตุส่วนบุคคล
- ค่ารักษาพยาบาล
- ช่วยเหลือฉุกเฉิน
- ลากรถ
- รถใช้ระหว่างซ่อม

ทุกหมวดสามารถบันทึกวงเงิน หน่วยหรือฐานของวงเงิน จำนวนครั้ง ระยะทาง เงื่อนไข และข้อยกเว้นได้

ค่า NULL ในวงเงินต้องแสดง “ยังไม่ระบุวงเงิน” ไม่ใช่ “ไม่จำกัด”

## 10. การค้นหา

### 10.1 ตัวกรอง

- คำค้นชื่อบริษัทหรือแพ็กเกจ
- บริษัทประกัน
- ประเภทประกัน
- ยี่ห้อ รุ่น และรุ่นย่อย
- อายุรถ
- การใช้งาน
- การซ่อม
- ช่วงเบี้ยรวม
- ช่วงทุนประกัน
- ความคุ้มครองที่ต้องการ

### 10.2 หลักการจับคู่

- ใช้ AND ระหว่างตัวกรองต่างชนิด
- ใช้ OR ภายในตัวกรองที่เลือกได้หลายค่า เช่น หลายบริษัท
- ความคุ้มครองที่เลือกเป็น “ต้องมี” ต้องผ่านครบทุกหมวด
- optional ไม่ถือว่าเป็นความคุ้มครองที่รวมในราคา
- ราคาและเงื่อนไขรถต้องตรงกันภายในตัวเลือกเดียวกัน
- ห้ามใช้ราคาของตัวเลือกหนึ่งร่วมกับความคุ้มครองของอีกตัวเลือก
- ข้อมูลไม่พอตัดสินให้แสดง “ต้องตรวจสอบเพิ่มเติม”
- ตัวกรองราคาไม่รวมรายการที่ไม่มีราคา เว้นแต่ผู้ใช้เลือกให้แสดง
- รายการหมดอายุไม่ปรากฏในผลค้นหาปกติ

### 10.3 การแสดงผล

ผลค้นหาอ้างอิง price_option_id เป็นหลัก เพราะหนึ่งแพ็กเกจมีหลายทุน ราคา และรูปแบบการซ่อมได้

แสดงข้อมูล:
- บริษัทและชื่อแพ็กเกจ
- รุ่นเงื่อนไข
- ประเภทประกัน
- ประเภทการซ่อม
- เบี้ยรวมและชนิดราคา
- ทุนประกัน
- ค่าเสียหายส่วนแรก
- ความคุ้มครองสำคัญ
- วันที่ตรวจสอบล่าสุด
- สถานะความครบถ้วน
- ปุ่มดูรายละเอียดและเลือกเปรียบเทียบ

ใช้ pagination เริ่มต้น 20 รายการต่อหน้า

การค้นหาชื่อภาษาไทยระยะแรกใช้ substring search เช่น ILIKE พร้อม parameterized query ไม่พึ่งการตัดคำภาษาไทยแบบ full-text

## 11. การเปรียบเทียบ

- เลือกตัวเลือกประกันได้ 2–4 รายการ
- ใช้ price_option_id เพื่อระบุตัวเลือกที่แน่นอน
- แสดงข้อมูลในรูปแบบคอลัมน์
- เปิดโหมดแสดงเฉพาะความแตกต่างได้
- เปิดดูเอกสารต้นทางได้
- ไม่จัดอันดับว่าแผนใดดีที่สุดโดยอัตโนมัติ

แสดงคำเตือนเมื่อ:
- ทุนประกันต่างกัน
- ประเภทการซ่อมต่างกัน
- ค่าเสียหายส่วนแรกต่างกัน
- ราคาอ้างอิงเงื่อนไขรถหรือผู้ขับขี่ต่างกัน
- ชนิดราคาแตกต่างกัน
- มีข้อมูลสำคัญที่ยังไม่ทราบ
- ราคาใดหมดอายุหลังจากถูกเลือกไว้

เมื่อเปิดหน้าเปรียบเทียบ ต้องอ่านสถานะล่าสุดจากฐานข้อมูลและตรวจสิทธิ์อีกครั้ง ไม่เชื่อข้อมูลที่ส่งมาจาก Browser

## 12. ขั้นตอนจัดการและเผยแพร่ข้อมูล

### 12.1 สถานะการทำงาน

| สถานะ | ความหมาย |
|---|---|
| draft | ข้อมูลร่าง แก้ไขได้ |
| in_review | รอตรวจสอบ ล็อกการแก้ไขทั่วไป |
| published | ตรวจสอบและเผยแพร่แล้ว |
| archived | เก็บย้อนหลัง ไม่ใช้ในผลค้นหาปกติ |

ข้อมูลไม่ผ่านการตรวจสอบให้ส่งกลับ draft พร้อมเหตุผล

สถานะหมดอายุและถึงกำหนดทบทวนคำนวณแยกจาก workflow_status โดยดูวันที่มีผลและ review_due_at

### 12.2 ขั้นตอนเผยแพร่

1. editor สร้างรุ่นข้อมูลร่าง
2. กรอกเงื่อนไข ราคา และความคุ้มครอง
3. แนบเอกสารอ้างอิง
4. ส่งตรวจสอบ
5. reviewer ตรวจเทียบเอกสารต้นทาง
6. ส่งกลับแก้ไขหรือเผยแพร่
7. บันทึกผู้ตรวจสอบ เวลา และเหตุผลที่เกี่ยวข้อง

### 12.3 การแก้ไขข้อมูลเผยแพร่แล้ว

- คัดลอกเป็นรุ่นร่างใหม่
- แก้ไขและตรวจสอบตามขั้นตอนเดิม
- เมื่อเผยแพร่รุ่นใหม่ ให้เปลี่ยนสถานะรุ่นเดิมที่ถูกแทนที่ใน transaction เดียวกัน
- เก็บรุ่นเดิมเพื่ออ่านย้อนหลัง
- หากข้อเสนอหลายชุดต้องใช้พร้อมกันและไม่ใช่การแทนที่กัน ให้แยกเป็นคนละแพ็กเกจหรือตัวเลือกที่มีขอบเขตชัดเจน

การเผยแพร่ต้องบันทึก audit log พร้อมการเปลี่ยนสถานะใน transaction เดียวกัน

## 13. การจัดการเอกสาร

- เริ่มต้นรองรับ PDF, PNG และ JPEG
- กำหนดขนาดไฟล์เริ่มต้นไม่เกิน 10 MB ต่อไฟล์
- ตรวจขนาด ชนิดไฟล์ และลักษณะเนื้อหาไฟล์ฝั่งเซิร์ฟเวอร์
- ตั้งชื่อจัดเก็บด้วย UUID ไม่ใช้ชื่อไฟล์เป็น path โดยตรง
- เก็บไฟล์ใน private bucket
- สร้าง signed URL อายุสั้นหลังตรวจสิทธิ์
- ไม่เก็บ signed URL เป็นลิงก์ถาวรในฐานข้อมูล
- viewer อ่านได้เฉพาะเอกสารของข้อมูลที่เผยแพร่หรืออนุญาตให้อ่านย้อนหลัง
- เอกสารของรุ่นเผยแพร่แล้วห้ามถูกแทนที่โดยตรง
- แนะนำบันทึกเลขหน้าหรือหัวข้อที่รองรับราคาและเงื่อนไขสำคัญ
- ปกปิดข้อมูลส่วนบุคคลที่ไม่จำเป็นก่อนอัปโหลด

หากอัปโหลดไฟล์สำเร็จแต่บันทึกฐานข้อมูลล้มเหลว ต้องลบไฟล์ค้างหรือมีงานตรวจเก็บไฟล์ที่ไม่มีรายการอ้างอิง

## 14. ความปลอดภัย

- ปิดการสมัครสมาชิกสาธารณะ
- จำกัดบัญชีด้วยการเชิญ
- เปิด RLS ในทุกตารางที่เข้าถึงผ่าน API
- ผู้ถูกปิดบัญชีต้องไม่อ่านข้อมูลได้แม้ยังมี session เดิม
- editor แก้ได้เฉพาะข้อมูลร่างและข้อมูลที่ได้รับสิทธิ์
- reviewer เผยแพร่ผ่าน operation ที่ตรวจข้อกำหนดครบ ไม่อัปเดตสถานะโดยตรง
- audit_logs เพิ่มโดยระบบ ผู้ใช้ทั่วไปแก้ไขหรือลบไม่ได้
- Storage ใช้นโยบายสิทธิ์สอดคล้องกับรุ่นข้อมูล
- ตรวจ input ฝั่งเซิร์ฟเวอร์ทุกครั้ง
- ไม่ใช้ raw SQL ที่ต่อข้อความจาก input
- ไม่แสดง HTML จากข้อมูลที่ผู้ใช้กรอกโดยไม่มีการทำให้ปลอดภัย
- ไม่บันทึกรหัสผ่าน token หรือกุญแจลับลง log
- ใช้ HTTPS เมื่อเปิดออนไลน์
- ไม่เปิด service-role key ใน Browser หรือในตัวแปร NEXT_PUBLIC_*
- ไม่ commit ไฟล์ .env.local

การตรวจสิทธิ์ต้องมีทั้งระดับหน้าจอ การทำงานฝั่งเซิร์ฟเวอร์ และฐานข้อมูล

## 16. ประสิทธิภาพและการสำรองข้อมูล

### 16.1 ประสิทธิภาพ

- ทำ index บน foreign key และคอลัมน์ที่กรองบ่อย
- ใช้ pagination ไม่โหลดข้อมูลทั้งหมด
- ดึงเฉพาะคอลัมน์ที่ต้องใช้ในผลค้นหา
- โหลดเอกสารเมื่อผู้ใช้กดเปิด
- เพิ่ม trigram index สำหรับการค้นหาชื่อเมื่อปริมาณข้อมูลทำให้จำเป็น

เป้าหมายทดสอบเบื้องต้น:
- ผู้ใช้พร้อมกัน 3 คน
- ตัวเลือกราคาทดสอบ 1,000 รายการ
- ผลค้นหาส่วนใหญ่แสดงภายในประมาณ 2 วินาทีภายใต้เครือข่ายและสภาพแวดล้อมทดสอบที่กำหนด

ตัวเลขนี้เป็นเป้าหมายที่ต้องวัด ไม่ใช่การรับประกันจากผู้ให้บริการ

### 16.2 การสำรอง

- สำรองฐานข้อมูลเป็นประจำ เป้าหมายเริ่มต้นรายวัน
- สำรองไฟล์เอกสารแยกจากฐานข้อมูล
- เก็บสำเนาไว้นอกระบบหลักและจำกัดสิทธิ์
- กำหนดระยะเก็บสำรอง เช่น 30 วัน ตามพื้นที่และงบประมาณ
- ทดลองกู้คืนก่อนเปิดใช้งานจริงและเป็นระยะ
- ตรวจว่าบริการที่เลือกมีความสามารถสำรองตามแผนหรือไม่

การสำรองฐานข้อมูลเพียงอย่างเดียวไม่ถือว่าได้สำรองไฟล์เอกสารแล้ว

| ไม่ทราบรุ่นรถที่รับ | ไม่ตีความว่าใช้ได้ทุกรุ่น |
| ราคาและรถตรงกันคนละตัวเลือก | ไม่แสดงเป็นตัวเลือกที่ตรงครบ |

| กู้คืนข้อมูลสำรอง | เปิดข้อมูลและเอกสารที่สัมพันธ์กันได้ |

ใช้ unit tests สำหรับกฎจับคู่และ validation, integration tests สำหรับฐานข้อมูลและ RLS และ end-to-end tests สำหรับเส้นทางใช้งานหลัก

- สร้าง migrations

- เชิญสมาชิก
- สร้าง RLS และทดสอบสิทธิ์
- เชื่อมหน้าจอกับฐานข้อมูล

### ระยะที่ 3: จัดการข้อมูล

- ทำแบบฟอร์มบริษัทและแพ็กเกจ
- เพิ่มรุ่นเงื่อนไข กฎรถ ราคา และความคุ้มครอง
- ทำ private document upload
- เพิ่ม workflow ตรวจสอบและ audit log

### ระยะที่ 4: ทดลองใช้งาน

- รวบรวมข้อมูลจริงประมาณ 10–20 แพ็กเกจ
- ตรวจข้อมูลกับเอกสารต้นทาง
- ให้สมาชิกทั้ง 3 คนทดลองใช้งาน
- ทดสอบข้อมูลไม่ครบและขอบเขตสิทธิ์
- ทดสอบสำรองและกู้คืน

### ระยะที่ 5: เปิดใช้งาน

- แยก development ออกจาก production
- ตั้งค่าความลับและบัญชี production
- ไม่ใส่ข้อมูลสมมติในระบบจริง
- เปิด HTTPS
- จัดทำคู่มือกรอกข้อมูลและตรวจสอบ
- ติดตามข้อผิดพลาดและปรับปรุงตามการใช้งาน

## 19. เกณฑ์พร้อมใช้งานเวอร์ชันแรก

- สมาชิกทั้ง 3 คนเข้าสู่ระบบได้
- ผู้ไม่มีสิทธิ์เข้าถึงฐานข้อมูลและเอกสารไม่ได้
- เพิ่มและเผยแพร่แพ็กเกจได้ครบวงจร
- ทุกชุดข้อมูลที่เผยแพร่มีแหล่งอ้างอิง
- ค้นหาด้วยตัวกรองหลักได้
- เปรียบเทียบได้ 2–4 ตัวเลือก
- ไม่ปะปนราคาและเงื่อนไขจากคนละตัวเลือก
- ข้อมูลไม่ทราบและข้อมูลหมดอายุแสดงถูกต้อง
- เก็บประวัติรุ่นและการแก้ไขได้
- ผ่านการทดสอบสำรองและกู้คืน
- มีผู้รับผิดชอบตรวจทบทวนข้อมูล

## 20. งานต่อยอด

- นำเข้า Excel พร้อมหน้าตรวจสอบก่อนบันทึก
- แจ้งเตือนข้อมูลใกล้หมดอายุหรือถึงกำหนดทบทวน
- บันทึกชุดเปรียบเทียบที่ใช้บ่อย
- ส่งออกผลเปรียบเทียบ
- เพิ่มข้อมูลอู่และศูนย์บริการ
- เชื่อม API เมื่อมีสิทธิ์และข้อตกลงที่ชัดเจน
- ใช้ AI ช่วยอ่านเอกสารโดยบันทึกเป็นข้อมูลร่างและให้คนตรวจเสมอ

## 21. ข้อจำกัดที่ต้องสื่อสารกับผู้ใช้งาน

ระบบนี้เป็นเครื่องมืออ้างอิงข้อมูลภายใน ไม่ใช่การยืนยันราคา การรับประกัน หรือความคุ้มครองสำหรับรถคันใดโดยอัตโนมัติ

ก่อนนำข้อมูลไปใช้งานจริง ต้องตรวจสอบเอกสารและเงื่อนไขที่มีผลกับบริษัทประกัน โดยเฉพาะรายการที่ไม่ครบ ถึงกำหนดทบทวน หรือมีข้อจำกัดเฉพาะกรณี
